Squad agêntica · AIOps · protótipo

Como o EasyRun funciona, peça por peça

Uma squad de oito agentes que detecta uma anomalia em produção, descobre a causa, decide o que o caso exige — ação de infraestrutura, correção de código, mudança de configuração ou escalonamento —, pede autorização humana quando o risco manda, executa e deixa o rastro que o processo da empresa cobra. Encaixada entre ServiceNow, Datadog, IUClick, Devin e GitHub. Este documento explica o produto, o código e o processo, sem pressupor conhecimento prévio.

Antes de tudo: o EasyRun é um protótipo. O dashboard é um mockup estático, o pacote Python é contrato de tipos com implementação vazia, e nada de AWS ou LangGraph existe ainda. Cada componente abaixo carrega um selo dizendo em que estágio realmente está.

01

Visão geral

O problema, a proposta e o que de fato existe hoje.

O problema

Quando um serviço quebra em produção, alguém precisa perceber, diagnosticar, decidir, executar e documentar. O ciclo tem uma métrica: MTTR, o tempo médio de reparo. A referência humana usada no projeto é de 38 minutos por incidente — e a maior parte desse tempo não é raciocínio difícil, é trabalho repetitivo.

A proposta

Seis agentes especializados cobrindo o ciclo inteiro, com duas ideias no centro: ações de alto risco param e pedem aprovação humana (HITL), e cada incidente resolvido vira memória para o próximo. No cenário de referência, o MTTR cai para 4m 32s.

02

Ambiente e ferramentas

O que é cada pasta de infraestrutura, por que existe e o que quebra sem ela.

Do zero ao mockup rodando

git clone https://github.com/adfshownet/EasyRun.git
cd EasyRun
python -m venv .venv                 # cria o ambiente virtual
.venv\Scripts\activate               # Windows
pip install -e ".[dev]"              # instala o projeto + pytest
pytest                               # 25 testes devem passar
squad-agentica-serve                 # abre localhost:8080

.venv/ — o ambiente virtual

Uma instalação isolada e privada do Python só para este projeto: interpretador, Lib/site-packages (todas as bibliotecas) e Scripts/ (os executáveis). O arquivo pyvenv.cfg traz a linha decisiva — include-system-site-packages = false — que é o que garante o isolamento.

Sem ela: o pip install vai para o Python do sistema, e três problemas aparecem — projetos brigando por versões incompatíveis da mesma biblioteca, ambiente irreprodutível (“funciona na minha máquina”) e poluição global irreversível.

Por que é gitignorada: é grande, tem caminhos absolutos da máquina, e é 100% reconstruível a partir do pyproject.toml. No Windows a pasta é Scripts/; no Linux e macOS, bin/.

pyproject.toml — a identidade

Descreve o projeto de forma declarativa: nome, versão, Python mínimo, extras e comandos. Substituiu o antigo setup.py, que era código executável.

[build-system]
Qual ferramenta constrói o pacote (setuptools, via PEP 517)
[project]
Nome, versão 0.1.0, requires-python = ">=3.10"
optional-dependencies
O extra dev = pytest>=8
[project.scripts]
Cria o comando squad-agentica-serve
packages.find
where = ["src"] — o código mora em src/

Note o que não está lá: nenhuma dependência obrigatória. O pacote roda só com a biblioteca padrão do Python.

pip install -e ".[dev]"

O . instala o projeto atual. O [dev] traz o extra com o pytest. E o -e — editable install — é o que mais importa no dia a dia: em vez de copiar os arquivos para dentro do ambiente, o pip grava um ponteiro para src/. Você edita o código e a próxima execução já usa a versão nova, sem reinstalar.

Artefatos descartáveis

egg-info/
Ficha do pacote gerada pelo setuptools a partir do pyproject.toml
__pycache__/
Bytecode compilado — só acelera a carga
.pytest_cache/
Resultado da última execução, habilita --last-failed

Todos gitignorados pelo mesmo princípio: são derivados, reaparecem sozinhos, e versioná-los criaria uma segunda fonte da mesma informação.

O truque do .gitignore que vale conhecer

.vscode/*
!.vscode/launch.json
!.vscode/tasks.json

Ignora tudo na pasta e depois abre exceções com !. A razão: settings.json costuma guardar preferência pessoal e não deve ser imposto ao time; já launch.json e tasks.json são infraestrutura compartilhada — é o que faz o F5 funcionar igual para todos. Detalhe do Git: a negação só funciona porque a regra usa /*; se ignorasse o diretório inteiro, o Git nem entraria nele.

03

Arquitetura do código

Cada módulo Python, com o conceito da linguagem explicado antes do código.

Mapa do repositório

EasyRun/ ├── src/squad_agentica/ ← o pacote Python │ ├── __init__.py 1 linha: a versão │ ├── serve.py servidor HTTP local [IMPLEMENTADO] │ └── aiops/ o contrato AIOps │ ├── severity.py enums de severidade [CONTRATO] │ ├── state.py o AgentState [CONTRATO] │ ├── roles.py os 4 papéis do grafo [STUB] │ ├── remediation.py mapa anomalia → ação [CONTRATO] │ ├── governance.py FinOps e modelos [CONTRATO] │ ├── checkpoint.py persistência de estado [STUB] │ └── graph.py o grafo LangGraph [STUB] ├── tests/ 25 testes (pytest) ├── prototype/ o mockup visual [MOCKUP] ├── docs/ esta documentação ├── pyproject.toml └── validate_zip.py script órfão de uma fase anterior

Por que o código mora em src/

Python resolve import olhando primeiro o diretório de onde você rodou o comando. Se o pacote estivesse na raiz, pytest encontraria a pasta local e nunca testaria o pacote instalado — mascarando erros de empacotamento que só apareceriam na máquina do usuário final.

Com src/, a única forma de o import funcionar é achando o pacote instalado. Consequência intencional: sem pip install -e, os testes nem coletam. Isso é feature, não bug.

O subpacote aiops/

MóduloConceito PythonO que defineEstado
severity.py class X(str, Enum) — o membro é uma string, serializa em JSON sem conversão Severity: crítico / alerta / preditivo · DetectionAlgorithm: basic / agile / robust Contrato
state.py TypedDict — em runtime é um dict comum; o contrato é verificado antes de rodar AgentState, 13 campos, incluindo schema_version Contrato
roles.py Callable class (__call__) — encaixa na assinatura que um nó de grafo espera Planner, Explainer, Validator, Coach e request_human_approval Stub
remediation.py @dataclass(frozen=True) — gera __init__/__eq__ e congela contra mutação REMEDIATION_MAP: 3 anomalias → ação → serviço AWS Contrato
governance.py Constantes puras, sem imports Modelos gold/mínimo, temperaturas, VRAM Contrato
checkpoint.py Dataclass + classe de repositório Checkpoint e CheckpointStore (PostgreSQL) Stub
graph.py — build_graph(); deliberadamente não importa langgraph Stub

Os 13 campos do AgentState

É o objeto que atravessa todo o fluxo. Três detalhes de design merecem atenção:

  • confidence guarda a confiança do diagnóstico (0,89 a 0,95 nos cenários) — o agente diz “causa provável”, não “a causa é”.
  • hitl_approved é Optional[bool] de propósito: None = ainda não perguntamos, False = rejeitado. Um booleano puro confundiria os dois.
  • schema_version existe porque, durante um deploy gradual, versões antiga e nova do contrato coexistem — e é preciso detectar isso em vez de quebrar com KeyError.

Por que os papéis levantam erro

Todo papel em roles.py tem corpo raise NotImplementedError — o idioma Python para “existe, mas ainda não”. E há um teste que garante que continue assim.

Parece estranho testar que um stub segue stub, mas é intencional: ninguém implementa um papel pela metade sem também remover o teste deliberadamente. O contrato fica congelado até a decisão consciente de destravá-lo.

Mapa de remediação e política de modelos

GatilhoAçãoServiço

Temperatura controla a aleatoriedade da geração de um LLM: perto de zero, determinístico; mais alto, mais variado. O teste não trava os números — trava a relação TEMPERATURE_VALIDATOR < TEMPERATURE_COACH, preservando o princípio sem engessar os valores.

serve.py — as 38 linhas que realmente executam

Sobe um servidor HTTP estático apontando para prototype/. Duas decisões interessantes num arquivo tão pequeno:

  • Cache-Control: no-store em toda resposta — sem isso você editaria o mockup, apertaria F5 e continuaria vendo a versão antiga do cache.
  • except KeyboardInterrupt: pass — Ctrl+C encerra em silêncio, sem despejar um traceback de erro para uma saída que é normal.

E uma armadilha: Path(__file__).resolve().parents[2] sobe três níveis para achar a raiz do repositório. Funciona no checkout; quebraria se o pacote fosse instalado normalmente em site-packages.

Frontend / protótipo

Como o dashboard funciona — e onde a ilusão começa e termina.

Tudo nesta seção é aparência. Não existe backend, não existe LLM, não existe AWS. Os 8 agentes, os 9 cenários, as métricas e os 156 passos de simulação estão escritos como literais dentro de um único arquivo HTML. O “chat com a squad” responde por correspondência de palavra-chave — e nenhuma linha de código fala com ServiceNow, Datadog, IUClick, Devin ou GitHub.

O runtime dc

Um micro-framework que permite escrever uma tela inteira num único HTML: o visual dentro de <x-dc>, a lógica numa class Component extends DCLogic. Ele carrega React 18.3.1 e Babel do CDN unpkg com SRI (o navegador confere o hash do script antes de executar) e acrescenta tags próprias ao HTML: <sc-for>, <sc-if>, <helmet>, e atributos style-hover para pseudo-classes que CSS inline não suporta.

As 9 telas

  • Console — cenários, agentes, log ao vivo, plano, memória, natureza e rastreabilidade
  • Chat da squad — conversa com o “Maestro”
  • Aprovações HITL — fila pendente, com layout por tipo de gate
  • Avaliação — métricas, distribuição por natureza, scores por agente
  • Configuração — agentes, guardrails, triggers, telemetria, política de código
  • Integrações — o que a squad lê e escreve em cada plataforma
  • LLMOps — observabilidade da própria esteira
  • FinOps — política de governança de modelos
  • Arquitetura — os 13 pilares, stack-alvo e integração

O motor de simulação

Um laço de setTimeout avança um passo a cada 1900 / velocidade milissegundos. Cada passo é um objeto que declara o agente, o pilar, o serviço AWS, o texto do log e — opcionalmente — efeitos colaterais e um portão de aprovação: 

{
  ag: 'auditor', pilar: '🛡️ Guardrails',
  txt: 'Guardrail G-02 interceptou o passo 2…',
  fx:   { agStatus: {…}, planoCriar: […], memoriaAdd: {…} },
  gate: { id: 'APR-01', risco: 'médio', detalhe: '$ easyrun executar rollback…' }
}

Quando o passo tem gate, o laço não é reagendado — a simulação congela de verdade até alguém clicar em Aprovar ou Rejeitar. Rejeitar não aborta: passos marcados como dinamico passam a usar um texto alternativo, e a squad segue com o plano B conservador.

Abaixo, cada etapa ancorada no cenário de referência ANM-2047 (latência no checkout-api).

01

Detecção

Sentinela · CloudWatch

“Latência p99 do checkout-api em 2.840 ms (limiar: 650 ms). Anomalia ANM-2047 aberta.”

p99 significa que 99% das requisições foram mais rápidas que esse valor — a métrica certa, porque a média esconde o 1% de clientes que abre chamado.

02

Evento no barramento

Sentinela · EventBridge

A Sentinela não chama o Maestro diretamente — ela anuncia o fato. Quem se interessar reage. Isso permite acrescentar consumidores depois sem tocar em quem publica.

03

Orquestração

Maestro · Step Functions

Decompõe em tarefas: recuperar contexto → diagnosticar → planejar → agir → avaliar. É uma máquina de estados: sabe o que vem depois, o que fazer se falhar e onde pode pausar.

04

Contexto e memória

Contexto · OpenSearch + DynamoDB

Duas camadas: semântica (runbooks vetorizados — “o que eu sei sobre latência de API”) e episódica (“já vi exatamente isso em março”). É a etapa que faz a squad melhorar com o tempo.

“INC-1893 teve a mesma assinatura logo após um deploy — resolvido com rollback (eficácia 96%).”

05

Diagnóstico de causa raiz

Diagnosta · IARA MCP

“Causa provável: esgotamento do pool de conexões RDS por vazamento introduzido no deploy v2.14.3. Confiança: 92%.”

Deploy às 14:00, pico às 14:02 — a correlação temporal é a pista principal. E a confiança é explícita: honestidade epistêmica embutida no design.

06

Plano de remediação

Maestro · Step Functions

Quatro passos, e a ordem revela pensamento: congelar deploys vem primeiro. Antes de corrigir, estanca a fonte — se alguém publicar outra versão no meio da remediação, o diagnóstico vira ruído.

07

O guardrail intercepta

Auditor

Guardrail é uma política determinística, avaliada fora do modelo. Não é o LLM decidindo se deve pedir permissão. Quatro estão definidos: aprovação humana para rollback, limite de 3 ações de escrita, escopo de ambiente e modo somente-leitura noturno.

08

A fila HITL — a execução para

decisão humana

O card traz quatro informações juntas de propósito: o quê (o comando exato), por quê (a justificativa com confiança), com que precedente (a memória) e qual o risco. O humano decide em segundos sem abrir cinco abas.

E rejeitar não é abortar: a squad tem um plano B conservador — reciclar as instâncias do pool sem reverter o deploy.

09

Execução

Executor · Lambda + SSM

Rollback v2.14.3 → v2.14.2 e escalonamento do pool RDS de 50 para 120 conexões. O único agente sem LLM, porque é o único que muda o mundo.

10

Validação

Sentinela · CloudWatch

Etapa frequentemente esquecida em automações: confirmar que funcionou. A latência cai de 2.840 ms para 610 ms — abaixo do limiar de 650 ms que abriu o alarme. O ciclo fecha contra o mesmo critério que o abriu.

11

Pós-mortem e aprendizado

Auditor · S3

APR-2047 — assinatura “pool RDS + deploy recente” → rollback prioritário.

O próximo incidente com essa assinatura já vai começar com a hipótese pronta. É o que separa uma automação de um sistema que aprende.

12

Encerramento

Maestro

MTTR: 4m 32s, contra 38 minutos de referência humana. A Sentinela volta a vigiar e o ciclo recomeça no próximo trigger.

Por que três rodam sozinhos

O critério de autonomia não é a severidade — é reversibilidade × custo do erro. O DNS é crítico e mesmo assim autônomo, porque failover de rota é trivialmente reversível e esperar custaria mais que errar; resultado, o menor MTTR dos nove. O disco roda sozinho pelo motivo oposto: é preventivo, sem urgência, e expandir volume é não-destrutivo. E o rolling restart do cenário Watchdog não muda versão nem configuração persistente — reversível por definição.

Por que o Watchdog importa

No ANM-2150 nenhum monitor cobria a métrica: o Watchdog do Datadog encontrou a anomalia por IA — vazamento lento de memória, três dias de degradação gradual — e o insight entrou na esteira como qualquer outro gatilho. O desfecho fecha o ciclo: além do alívio em runtime, a squad cria o monitor permanente que faltava e abre card preventivo para a causa de fundo. Detecção por IA como rede de segurança, não como substituto de cobertura.

Por que a natureza muda tudo

Um sistema que só soubesse agir em infraestrutura teria reiniciado o frete-service do INC-3312, visto os erros sumirem e fechado o incidente. O defeito continuaria no código e voltaria no próximo pico — com o agravante de existir um registro dizendo que "foi resolvido". Classificar como CODIGO é o que impede esse falso positivo.

Por que saber desistir é um resultado

O INC-3377 termina sem que a squad conserte nada, e isso é o comportamento correto: a falha está no gateway de um adquirente, fora do perímetro. A squad isola, prova que o problema não é nosso, propõe um workaround com o custo explícito, aceita a recusa e escala formalmente. Numa apresentação, é o cenário que responde à pergunta mais difícil da sala.

Por que o ramo de código para duas vezes

Aprovar um patch e aprovar uma janela de mudança em produção são autoridades diferentes, exercidas por pessoas diferentes. Fundir as duas não sobrevive ao primeiro comitê de mudança. E se o PR é rejeitado, o gate da GMUD nem aparece — não se pede janela para um patch recusado. O número de gates, porém, segue o nível de risco da classe de mudança: alto risco = 2 gates; baixo risco = 1 gate consolidado (o APR-05 avalia parâmetro e janela na mesma decisão); histórico comprovado no golden set = promoção até a auto-aprovação — exceto a GMUD, sempre humana.

Por que o cenário-espelho existe

No ANM-2210, a dependência que falha é o próprio gateway IARA — o único caminho de LLM da squad. O circuit breaker abre, os papéis de raciocínio param, e a squad opera em contingência: zero chamadas de modelo, só runbooks determinísticos pré-aprovados (gate APR-07, guardrail G-08) e escalonamento humano — nunca bypass para provedor direto. Quem carrega o incidente na janela é o Step Functions, dono do estado durável; o diagnóstico vem a posteriori, quando o circuito fecha.

LangGraph estrutura aplicações com LLM como grafos de estado: nós (unidades de trabalho), arestas condicionais, um estado compartilhado que atravessa tudo, interrupt() para pausar, e um checkpointer para retomar.

A armadilha documentada no código: depois de um interrupt(), o nó precisa devolver o AgentState completo. O nó seguinte recebe um estado sem incident_id e falha com um erro que aponta para o lugar errado.

O contrato de propriedade do estado

Step Functions e LangGraph são ambos máquinas de estado — e duas máquinas de estado governando o mesmo fluxo terminam em corrupção de dados ou execuções zumbis na primeira pausa HITL. O contrato que resolve a ambiguidade:

1 · Step Functions é o dono

Do estado durável: lifecycle, retries, integrações e a pausa HITL via task token (waitForTaskToken) — o callback humano retoma a máquina do ponto exato, mesmo dias depois.

2 · LangGraph é efêmero

O grafo nasce e morre dentro de uma invocação de task: recebe o estado, raciocina, devolve o AgentState serializado. O checkpointer PostgreSQL protege só o progresso intra-invocação.

3 · Um dono por vez

Dentro da task, o dono é o grafo; fora dela, o Step Functions. interrupt() não atravessa fronteira de invocação — espera longa é sempre task token. Resolve a lacuna #12.

CI/CD e Git

O que roda quando você dá push — e o que não roda.

tests.yml Ativo

Dispara em push e pull request, filtrado por paths: src/, tests/, pyproject.toml e o próprio workflow. Monta um Ubuntu limpo, instala Python 3.12, roda pip install -e ".[dev]" e pytest.

Traz permissions: contents: read — princípio do menor privilégio. O job só precisa ler o código, então o token não pode escrever no repositório.

validate-zip.yml Inerte

Roda validate_zip.py quando algo muda em uploads/ — só que essa pasta foi removida do repositório. O filtro nunca casa e, se casasse, o script imprimiria “nothing to validate” e retornaria sucesso.

É herança de uma fase anterior do projeto, quando havia um protótipo de upload em Express. Na aba Actions o repositório aparenta ter duas verificações; tem uma.

Glossário

Os termos técnicos do EasyRun, incluindo os das plataformas da empresa. Digite para filtrar.

A2A — Protocolo para agentes de frameworks diferentes se descobrirem e conversarem, via um Agent Card em .well-known/agent-card.json.
Agente — Programa que combina um modelo de linguagem, ferramentas e alguma autonomia para agir. Diferente de um chatbot, ele executa ações.
AgentState — O TypedDict de 13 campos que carrega o contexto do incidente por todo o fluxo. O contrato central da arquitetura.
AIOps — Inteligência artificial aplicada à operação de TI: detectar anomalias, diagnosticar causas, remediar automaticamente.
Ambiente virtual (venv) — Instalação isolada do Python para um projeto, na pasta .venv/. Impede que as dependências de projetos diferentes colidam.
ASG (Auto Scaling Group) — Serviço AWS que mantém um número desejado de instâncias EC2, adicionando ou removendo conforme a demanda.
Autonomia por nível de risco — O número de gates HITL é função do tier de risco da classe de mudança (governance.RiskTier): alto = 2 gates, baixo = 1 consolidado, histórico comprovado = promoção até auto-aprovação — exceto a GMUD, sempre humana.
Bedrock — Serviço AWS de modelos de linguagem gerenciados (Claude, Titan), sem gerenciar GPU. No EasyRun os agentes não o acessam diretamente: toda chamada de LLM sai pelo MCP do IARA.
Bounded context — Fronteira dentro da qual cada termo do domínio tem um significado único. Conceito central do DDD.
Bytecode — Forma compilada intermediária de um .py, guardada em __pycache__/. Só acelera a carga.
Cache-Control — Cabeçalho HTTP sobre armazenar ou não a resposta. O serve.py envia no-store para que edições apareçam sem F5 forçado.
Callable class — Classe que define __call__ e pode ser chamada como função. É como os papéis do grafo são declarados.
Checkpoint — Fotografia durável do estado, para retomar dali em caso de falha. Crítico quando as ações já executadas são irreversíveis.
CI/CD — Verificação automática de cada mudança (CI) e publicação automática do que passou (CD). Este projeto tem só CI.
Circuit breaker — Interrompe tentativas após N falhas seguidas, evitando retry storms contra um serviço já saturado. O EasyRun mantém um dedicado à saúde do gateway IARA: abri-lo ativa o modo de contingência (cenário ANM-2210).
Console script — Mecanismo que transforma uma função Python em comando de terminal. Gera o squad-agentica-serve.
dataclass — Decorador que gera __init__, __repr__ e __eq__ de uma classe de dados. Com frozen=True, torna-a imutável.
DDD (Domain-Driven Design) — Modelar o software na linguagem do negócio, organizado em bounded contexts.
Editable install — pip install -e: instala por ponteiro em vez de cópia, então editar o código-fonte reflete na hora.
egg-info — Metadados gerados pelo setuptools na instalação. Artefato derivado, por isso gitignorado.
Embedding — Texto representado como vetor numérico, de modo que significados próximos fiquem próximos no espaço. Viabiliza a busca semântica.
Enum — Tipo com conjunto fixo e nomeado de valores. Elimina “strings mágicas” e transforma erro de digitação em falha imediata.
EventBridge — Barramento de eventos da AWS. Publica anomalia.detectada.
Exit code — Número devolvido ao sistema operacional: 0 = sucesso. É como o CI decide se um step passou.
Failover — Redirecionar tráfego para um recurso reserva quando o principal falha. A remediação para dns_timeout.
FastAPI — Framework web Python assíncrono que gera documentação OpenAPI a partir das anotações de tipo.
FinOps — Gestão financeira de nuvem. No contexto de IA: escolha de modelo, orçamento de tokens, local vs. nuvem.
GitHub Actions — Sistema de CI integrado ao GitHub, configurado por arquivos YAML em .github/workflows/.
Guardrail — Política explícita e determinística que limita o que os agentes podem fazer sozinhos. Avaliada fora do modelo.
Hardening — Medidas que tornam um sistema apto a produção: versionamento de schema, circuit breakers, auditoria imutável, sanitização.
Hexagonal (ports and adapters) — Arquitetura que isola o domínio das tecnologias externas por trás de interfaces.
HITL (Human-In-The-Loop) — Humano no circuito: a execução automática para e aguarda decisão humana. O mecanismo central de segurança do EasyRun.
IARA — Time (e solução interna) que governa o acesso e o custo de LLMs na empresa. Expõe um gateway MCP pelo qual os agentes fazem toda requisição de inferência — nenhum agente fala direto com provedor de modelo.
Idempotente — Operação que, executada duas vezes, produz o mesmo resultado que uma. Requisito para remediação automática segura.
Injeção de prompt — Ataque em que texto de fonte não confiável contém instruções que o modelo obedece.
interrupt() — Função do LangGraph que suspende o grafo, persiste o estado e devolve o controle. No contrato de propriedade do estado, encerra a invocação da task — a espera longa pelo humano é sempre task token do Step Functions.
LangGraph — Framework que estrutura aplicações com LLM como grafos de estado, com nós, arestas condicionais, interrupt() e checkpointing.
LLM-as-judge — Técnica em que um modelo julga a qualidade da saída de outro. Necessária quando não há resposta única esperada.
MCP (Model Context Protocol) — Protocolo aberto que padroniza o acesso de modelos a ferramentas e fontes de dados externas.

Lacunas e riscos

Nenhum destes é bug de execução — hoje tudo roda. São riscos de manutenção: o tipo de problema que só aparece quando alguém edita a coisa errada seis meses depois.

Armadilhas silenciosas — quebram sem avisar

Fonte da verdade duplicada

REMEDIATION_MAP e governance.py existem também escritos à mão dentro do HTML do mockup. Alterar um não muda o outro, e nenhum teste percebe — porque o teste só olha o Python. Já há divergência de redação entre as duas cópias.

O problemMatcher e o print()

Contrato invisível entre dois arquivos que não se referenciam. Reescrever a mensagem de log faz o F5 travar esperando eternamente — e o sintoma não aponta para a causa.

export/ era espelho manual resolvida

Hoje o espelho é gerado por tools/sync-export.mjs (três diferenças estruturais conhecidas: script src, link do CSS e thumbnail) e o check-prototype.mjs compara os dois no CI a cada push.

O F5 só funciona no Windows

O tasks.json fixa .venv/Scripts/python.exe. Como é um arquivo versionado deliberadamente, é infraestrutura compartilhada — que serve a metade do time.

Falsa sensação de cobertura

validate-zip.yml não valida nada

A pasta uploads/ não existe mais. O workflow sempre passa sem testar coisa alguma.

O CI testa só Python 3.12

Mas o pyproject.toml promete >=3.10. A compatibilidade com 3.10 e 3.11 não é verificada por ninguém. Uma matriz de versões resolveria.

Resolvida nesta rodada — #12, o dono do estado

"Step Functions e LangGraph se sobrepõem" deixou de ser decisão em aberto: o contrato de propriedade do estado (seção 06) define que o Step Functions é o dono único do estado durável e da espera HITL (task token), e o LangGraph roda efêmero dentro de cada task — um único dono do estado por vez. Os docstrings de graph.py e checkpoint.py refletem o contrato.

O conceito que roteia tudo. Depois da causa raiz, o Diagnosta classifica o que o problema exige — e é isso que decide quem executa, quais gates sobem e qual é o artefato final.

NaturezaO que significaQuem executaDesfecho
INFRAAção em runtime na infraestruturaExecutor ⚡Comando aplicado
CÓDIGOO software precisa mudarArtífice 🛠️ → DevinPull request
CONFIGParâmetro, feature flag ou dadoExecutor ⚡Mudança sob GMUD

Errar essa classificação é o erro mais caro do fluxo: rotear infraestrutura para o caminho de código gasta uma sessão do Devin à toa; rotear código para o caminho de infraestrutura “resolve” o sintoma e o bug volta no próximo deploy.

A CMDB é o que torna a correção de código possível

O campo mais importante que a squad lê não é o nome do serviço nem o time dono — é qual repositório sustenta aquele item de configuração. Sem esse vínculo, o Artífice não tem o que clonar e o ramo de código não existe. Na prática, é o campo com maior chance de estar vazio ou desatualizado num CMDB real: a esteira precisa degradar escalando com o diagnóstico pronto.

Nem tudo está na AWS

O EasyRun roda na AWS, mas o incidente pode estar num ERP on-premises ou num serviço de terceiro. Por isso o desfecho final nem sempre é um comando de nuvem — pode ser um pull request, uma GMUD ou um escalonamento. O Executor não presume nuvem: age pela API do próprio sistema quando é o caso.

A fronteira que resume o produto: a squad abre a GMUD sozinha, mas nunca a aprova. Gera o pull request, mas nunca faz o merge. O ganho é de tempo de preenchimento — 48 segundos contra ~25 minutos —, não de controle.

Gates por nível de risco

Quantos gates uma mudança atravessa é função do tier de risco da classe (governance.RiskTier), não uma constante — porque exigir duas aprovações de tudo gera fadiga de aprovação: o humano que aprova tudo duas vezes aprende a aprovar sem ler.

Alto risco · 2 gates

Código em produção para duas vezes (PR e GMUD): conteúdo técnico e janela de risco são autoridades distintas. É o INC-3312.

Baixo risco · 1 gate consolidado

Janela padrão + rollback automático testado: conteúdo e janela avaliados na mesma decisão. É o APR-05 do INC-3350.

Histórico comprovado · promoção

Classe de baixo risco com histórico no golden set sobe por shadow → canário → produção até a auto-aprovação — exceto a GMUD, sempre humana.

A calibração é contínua: cada decisão HITL vira dado rotulado e realimenta a revisão dos tiers. No protótipo, cada card da fila exibe o chip RISCO ALTO / RISCO BAIXO.

Observabilidade da própria esteira, avaliação e rollout seguro de agentes.

Há duas observabilidades neste sistema, e confundi-las é o erro mais comum. O Datadog observa os sistemas monitorados — isso é a entrada da squad. Esta seção é sobre observar a squad: qual prompt rodou, quanto custou, se o diagnóstico estava certo.

Os nove conceitos

🧵 Trace único ponta a ponta

O mesmo trace_id atravessa Datadog APM, LangSmith e Langfuse e é gravado no incidente do ServiceNow. De “por que a squad reverteu meu deploy às 3h?” até a chamada de modelo exata são dois cliques.

📌 Prompts versionados

Prompt é artefato, não literal no código: versionado, promovido por ambiente e referenciado por id. Sem isso não há como saber, três meses depois, qual prompt produziu uma decisão.

🥇 Golden set de incidentes

Incidentes encerrados do ServiceNow viram casos de avaliação offline. O conjunto cresce sozinho: o que a squad resolve hoje é o teste de regressão de amanhã.

⚖️ LLM-as-judge com portão

Um modelo julga a qualidade do diagnóstico a temperatura 0.1. Versão candidata só é promovida se não piorar — e errar a natureza da remediação tem limiar próprio, mais rígido.

👻 Shadow mode e canário

A versão nova roda sobre incidentes reais registrando o que faria, sem agir. Só depois de um histórico comparável assume tráfego. É o que torna autonomia aceitável num ambiente avesso a risco.

🔁 Feedback loop do HITL

Cada aprovação e rejeição, com a justificativa, vira dado rotulado. A fila HITL não é só um portão de segurança: é a principal fonte de supervisão do sistema — e o que calibra o nível de risco dos gates: aprovação sem ressalva por meses rebaixa o tier; rejeição é evidência do contrário.

📉 Drift em dois níveis

Nos baselines de detecção e na precisão do agente ao longo do tempo. O segundo é o perigoso, porque nada quebra — a qualidade só escorrega.

🧽 Redação antes da saída

Código e logs passam por remoção de segredos e dados pessoais antes de ir a um agente externo. É a primeira objeção de segurança, e precisa de resposta no contrato, não no adaptador.

🎟️ Orçamento por execução

Teto de tokens por agente e por incidente, com corte automático. Um agente em laço não vira uma fatura surpresa.
